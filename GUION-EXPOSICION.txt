GUION DE EXPOSICIÓN
NEXO PARA DULCE RINCÓN - ACTIVIDADES 10 Y 11
Duración aproximada: 10 a 12 minutos, según el tiempo de la demostración.

Las indicaciones entre corchetes son acciones para quien expone; no se leen.
El texto se puede repartir entre dos integrantes al terminar cada apartado.

ACLARACIÓN ANTES DE PRESENTAR
La versión Laravel YA tiene una base de datos funcional: SQLite.
La conexión a un servidor PostgreSQL todavía no se ha probado ni implementado
como configuración activa de esta entrega. Si PostgreSQL es obligatorio en la
rúbrica, ese requisito sigue pendiente.
Antes de exponer, verificar que esta versión esté subida a la rama que se compartirá
con el profesor. El estado de GitHub debe confirmarse en el repositorio.
El enlace de internet de la primera maqueta es una versión diferente: no ejecuta
el backend Laravel de esta entrega.

- Tener a la mano el código fuente y este guion.
- Usar datos ficticios durante la demostración.
- Cuenta de administración: ana@dulcerincon.demo

1. PRESENTACIÓN DEL PROYECTO
======================================================================
[MOSTRAR: pantalla de login.]

"Buenos días. Vamos a presentar Nexo, un CRM pensado para la pastelería
Dulce Rincón.

El problema que busca resolver es la dispersión de información: un pedido puede
estar en WhatsApp, los datos del cliente en una libreta y las indicaciones del
pastel en otro lugar. Esto dificulta dar seguimiento y coordinar a mostrador
con cocina.

Nexo reúne esa información en un mismo sistema. Este avance corresponde a las
actividades 10 y 11: usuarios, clientes, seguridad básica, contactos, seguimiento
de ventas y registro de actividades."

2. QUÉ CAMBIÓ RESPECTO AL PRIMER AVANCE
======================================================================
[MOSTRAR: carpeta del proyecto y después volver al login.]

"El primer avance era una maqueta navegable en HTML, CSS y JavaScript. Permitía
revisar el diseño, pero el acceso era simulado y los ejemplos se guardaban en el
navegador.

La versión actual incorpora PHP y Laravel para procesar las operaciones en el
servidor, además de una base SQL real con SQLite. Ahora el registro, el login y
la captura de información tienen persistencia en la base de datos.

También se reorganizó el código por módulos y se formatearon los estilos para
que las reglas se puedan leer por separado. Las guías están en archivos de
texto comunes."

9. SEGURIDAD BÁSICA
======================================================================
[MOSTRAR brevemente un formulario o la pantalla Mi equipo.
Si hay tiempo: cerrar sesión y entrar como Cocina para comparar permisos.]

"La seguridad se aplica en el servidor, además de lo que se muestra en pantalla.
No basta con ocultar un botón: Laravel vuelve a comprobar el usuario y el rol
antes de permitir una operación.

Las contraseñas se guardan como hash, no como texto legible. Hay validación de
formularios, protección CSRF y un límite de intentos de acceso.

Las rutas del CRM exigen una sesión y una cuenta activa. Al cerrar sesión se
invalida ese acceso. Además, las consultas filtran por el negocio de la cuenta,
y cocina solo puede consultar las ventas que tiene asignadas."

10. ORGANIZACIÓN DEL CÓDIGO
======================================================================
[MOSTRAR routes/web.php y ClienteController.php. Luego abrir el formulario
de clientes y public/css/estilos.css.]

"El proyecto sigue la organización de Laravel.

Las rutas relacionan una dirección con una acción. Los controladores reciben
los formularios, comprueban permisos y validan datos. Los modelos representan
las entidades de la base. Las vistas Blade contienen el HTML de las pantallas.

Por ejemplo, guardar un cliente envía el formulario a una ruta. Esa ruta llama
al controlador de clientes, que valida la información y utiliza el modelo para
guardarla. Después muestra la ficha del registro.

El CSS controla la apariencia. JavaScript se usa para detalles visuales, como
abrir el menú o mostrar la contraseña; no decide los permisos de seguridad.
Las migraciones describen cómo crear las tablas y los seeders cargan ejemplos
para practicar."

PREGUNTAS QUE PODRÍA HACER EL PROFESOR
======================================================================

¿Ya tiene base de datos?
Sí. Esta versión usa SQLite y guarda datos SQL reales en database/database.sqlite.
El archivo se crea al preparar la aplicación; la primera ejecución instala las
tablas y puede cargar los ejemplos.

¿Entonces qué falta de PostgreSQL?
Configurar una base PostgreSQL real, conectar las credenciales locales y ejecutar
y verificar las migraciones y operaciones. Todavía no se ha probado ese motor.
Cambiar la configuración no copia por sí solo los datos que existan en SQLite.

¿Cuál es la diferencia entre SQL, SQLite y PostgreSQL?
SQL es el lenguaje para trabajar con datos. SQLite y PostgreSQL son motores de
base de datos. En esta entrega está funcionando SQLite; PostgreSQL era el motor
contemplado para la integración siguiente.

¿El sitio de internet y esta aplicación son lo mismo?
No. El enlace de la primera entrega contiene la maqueta visual. La versión
Laravel se inicia con el paquete de Windows y funciona en el servidor local.

¿Qué significa localhost o 127.0.0.1?
Es la dirección de esta misma computadora. El navegador se comunica con el
servidor PHP que está corriendo aquí. No significa que la aplicación ya esté
publicada para otras computadoras.

¿Se pierden los datos si cierro el navegador?
No. Están en la base local. Para volver a consultar la aplicación, el servidor
debe estar encendido y utilizarse la misma base. Borrar el archivo de la base
sí elimina esos datos locales.

¿Por qué Laravel?
Porque proporciona una estructura para las rutas, modelos, vistas, validación,
sesiones y acceso a la base. El código propio implementa las reglas del CRM
apoyándose en esas herramientas del framework.

¿Se guarda la contraseña tal como se escribe?
No. Se guarda un hash y se comprueba al iniciar sesión. No se debe presentar
el hash como si fuera una contraseña cifrada que se puede leer de regreso.

¿Ocultar un botón es suficiente para proteger una acción?
No. Los controladores y las comprobaciones de sesión vuelven a validar el rol.
Las consultas también limitan los registros al negocio de la cuenta.

¿Qué diferencia hay entre cliente, contacto, venta y actividad?
Cliente: quien compra. Contacto: la persona con quien se habla.
Venta: la oportunidad o pedido que se sigue en el embudo.
Actividad: la llamada, nota, tarea o interacción registrada.

¿Archivar un cliente borra sus pedidos?
No. Cambia su estado y conserva el historial. Retirar una persona de contacto
usa borrado lógico, que es una operación distinta de borrar definitivamente.

¿El monto en pedidos es dinero cobrado?
No. Es el monto de ventas abiertas en Pedido y Entrega. El anticipo se registra
por separado y el cierre de la venta no realiza un cobro bancario.

¿Ya está listo para usarse como sistema de producción?
La entrega demuestra los módulos y su seguridad básica en entorno local.
Antes de un uso real por internet faltaría desplegar Laravel, configurar HTTPS,
respaldos y revisar los requisitos de operación. No se han implementado
recuperación de contraseña por correo, verificación de correo ni doble factor.

¿Dónde se revisa que funcionan los módulos?
En tests/Feature/ModulosCrmTest.php. Las pruebas se ejecutan desde el proyecto
con php vendor/bin/phpunit. El paquete Windows también incluye
PROBAR-MODULOS.cmd. Las pruebas usan una base temporal en memoria.
